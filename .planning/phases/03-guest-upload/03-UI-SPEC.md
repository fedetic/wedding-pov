# Phase 3 — UI Design Contract: Guest Upload

> Visual and interaction contract for Phase 3 (Guest Upload). Generated by gsd-ui-researcher, verified by gsd-ui-checker.
> **This page is the core value of the product.** Guests experience it once, on a phone, at a wedding. Every decision here prioritises simplicity, legibility, and warmth over feature density.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none — hand-rolled Tailwind v4 utility classes (consistent with Phases 1 & 2) |
| Preset | not applicable |
| Component library | none — no Radix, no shadcn |
| Icon library | none — Unicode symbols and emoji only (✓, ×, →, 🎉) |
| Font | Geist Sans via `next/font/google` — already loaded in root `layout.tsx` |

**Design direction:** The guest upload page is intentionally distinct from the organizer dashboard. Phase 2 (organizer) is desktop-first, black/white/gray, functional. Phase 3 (guest) is mobile-first, warm off-white, celebratory. Same font; different palette, different scale, different emotional register.

---

## Spacing Scale

Same 8-point grid as Phase 2. Mobile-first exceptions declared explicitly.

| Token | px value | Tailwind class | Usage |
|-------|----------|----------------|-------|
| xs | 4px | `gap-1`, `p-1` | Icon gaps, inline padding |
| sm | 8px | `gap-2`, `p-2` | Compact element spacing |
| md | 16px | `gap-4`, `p-4` | Default element spacing, input horizontal padding |
| lg | 24px | `gap-6`, `px-6` | Page horizontal padding on mobile, section padding |
| xl | 32px | `gap-8`, `mt-8` | Step heading top margin, between-step separation |
| 2xl | 48px | `py-12` | Page vertical padding (top and bottom) |
| 3xl | 64px | not used this phase | Reserved |

**Exceptions (mobile-first):**
- Primary CTA button: `min-h-[56px]` (56px) — large touch target; the most critical interaction element
- Text inputs: `min-h-[52px]` (52px) — comfortable touch entry on iOS Safari
- All interactive elements: `min-h-[44px]` absolute floor — non-negotiable for mobile accessibility (WCAG 2.5.5)
- Photo thumbnail in upload progress list: `40×40px` (`w-10 h-10`) — compact but visually confirms file identity
- Progress bar track height: `4px` (`h-1`) — decorative only, not a touch target
- Accent decorative rule below event name: `2px × 32px` — not on spacing scale; purely decorative

## Typography

Larger than Phase 2 — mobile reading distance and visual hierarchy on a phone screen require more aggressive sizing.

| Role | Size | Tailwind | Weight | Tailwind | Line Height | Usage |
|------|------|----------|--------|----------|-------------|-------|
| Body | 16px | `text-base` | 400 | `font-normal` | 1.6 | Supporting text, step subtexts, error bodies |
| Label | 14px | `text-sm` | 600 | `font-semibold` | 1.25 | File count indicator, photo names, status labels |
| Step heading | 28px | `text-3xl` | 600 | `font-semibold` | 1.2 | Each step's primary heading ("What's your name?", "Choose your photos", etc.) |
| Display | 36px | `text-4xl` | 600 | `font-semibold` | 1.15 | Completion screen only — "You're all done! 🎉" |

Secondary/muted text: `text-base text-gray-500` — 16px, weight 400. Used for step subtexts and error explanations.

**Font weights in use: 2** — `font-normal` (400) for body and input text; `font-semibold` (600) for all headings, CTAs, and labels. Size alone carries hierarchy within the 600-weight group.

**Phase 2 comparison:** Phase 2 page heading is 24px. Phase 3 step heading is 28px because the guest page is full-bleed mobile — headings must be legible on a phone held at arm's length at a noisy venue.

## Color

Intentionally different from Phase 2. Warm, celebratory, wedding-appropriate.

| Role | Hex | Tailwind / inline | Usage |
|------|-----|-------------------|-------|
| Dominant (60%) | `#faf9f7` | `bg-[#faf9f7]` | Page background — warm off-white (distinct from Phase 2's stark `#ffffff`) |
| Secondary (30%) | `#ffffff` | `bg-white` | Input fields, progress item cards — white surfaces float on warm background |
| Accent (10%) | `#b85c52` | `bg-[#b85c52]` / `text-[#b85c52]` | Primary CTA buttons, progress bar fill, per-photo completion checkmark |
| Destructive | `#dc2626` | `text-red-600` / `bg-red-50` | Error banners only — same as Phase 2 for semantic consistency |

**Accent (`#b85c52`) reserved for:**
1. Primary CTA buttons (`bg-[#b85c52] text-white`): "Continue →", "Upload N photos →", "Try again"
2. Upload progress bar fill
3. Per-photo completion checkmark (✓) — appears after each photo finishes
4. Decorative accent rule below event name (2px × 32px)

**Never use accent for:** borders, text links, badges, decorative backgrounds, or secondary buttons.

**Borders:** `border border-gray-200` (`#e5e7eb`) on all cards and inputs — 1px solid, consistent with Phase 2.

**Progress bar track:** `bg-[#f0ebe9]` (warm light gray) — matches warm background palette. NOT the cold `bg-gray-200` used in Phase 2.

**Rationale for `#b85c52`:** Warm terracotta-rose — celebratory without being cliché pink, works for diverse wedding aesthetics, reads clearly on white and off-white backgrounds.

## Page Layout — `/e/[slug]`

**Route:** `/e/[slug]`
**Architecture:** Server Component shell (loads event data, validates slug, renders initial state) + Client Component for the upload state machine
**Pattern:** Single-page state machine — no browser navigation between steps; steps transition in place
**Mobile-first container:**

```
<main class="min-h-screen flex flex-col items-center justify-center bg-[#faf9f7]">
  <div class="w-full max-w-sm px-6 py-12">
    {/* step content */}
  </div>
</main>
```

**Max content width:** 384px (`max-w-sm`) — fits iPhone 12/13/14 (375px) and Samsung Galaxy (360px) with 24px padding on each side at minimum.

**No navigation header. No footer.** Guests see only the current step. No way to get lost.

```
│  │ [▣]  IMG_0042.jpg          ✓     │  │  rounded-xl px-4 py-3 — COMPLETE (✓ in #b85c52)

│  └──────────────────────────────────┘  │  track: bg-[#f0ebe9]; fill: bg-[#b85c52]
│  ┌──────────────────────────────────┐  │  ← PENDING (not yet started)
│  │ [▣]  IMG_0044.jpg                │  │  opacity-40 (dimmed, will upload next)
│  └──────────────────────────────────┘  │
│  ┌──────────────────────────────────┐  │
│  │ [▣]  IMG_0045.jpg                │  │  opacity-40
│  └──────────────────────────────────┘  │
│  ┌──────────────────────────────────┐  │
│  │ [▣]  IMG_0046.jpg                │  │  opacity-40
│  └──────────────────────────────────┘  │
│                                        │
│  [no CTA — user cannot interrupt]      │
└────────────────────────────────────────┘
```

**Per-photo states:**
- **Pending:** card with thumbnail + filename; `opacity-40`; no progress bar
- **In progress:** card with thumbnail + filename; full-opacity; progress bar below filename; `{N}%` text right-aligned in `text-sm text-gray-500`
- **Complete:** card with thumbnail + filename + `✓` right-aligned in `text-sm font-semibold text-[#b85c52]`; progress bar replaced by checkmark
- **Failed:** card with thumbnail + filename + `×` right-aligned in `text-sm font-semibold text-red-600`

**Upload strategy:** Sequential (one XHR at a time), not parallel. Mobile networks are unstable; sequential prevents partial failures from compounding.

**Progress animation:** CSS `transition-[width] duration-150 ease-out` on the fill `<div>` — smooth but not distracting.

**"Photo X of Y" counter:** Updates as each photo completes. Positioned above the photo list.

## Interaction Contracts

### State machine

```
LOADING (server data fetch)
  ├── event not found → ERROR_NOT_FOUND (terminal)
  ├── event inactive  → ERROR_INACTIVE (terminal)
  └── event active    → STEP_NICKNAME

STEP_NICKNAME
  └── (nickname entered + Continue) → STEP_SELECT

STEP_SELECT
  ├── (0 files chosen) → stays in STEP_SELECT
  ├── (over limit)     → STEP_SELECT with over-limit error
  └── (1–N files, valid) + "Upload" → STEP_UPLOADING

STEP_UPLOADING
  ├── (all succeed) → STEP_COMPLETE (terminal)
  └── (any fail)   → ERROR_UPLOAD (retry → STEP_SELECT)

STEP_COMPLETE (terminal — no exit)
ERROR_UPLOAD → retry → STEP_SELECT
```

### File input on iOS Safari

```tsx
// Correct implementation:
<input
  type="file"
  accept="image/*,.HEIC,.heic"
  multiple
  className="sr-only"
  ref={fileInputRef}
  onChange={handleFilesSelected}
/>
<button
  type="button"
  onClick={() => fileInputRef.current?.click()}
  className="..."
>
  Select photos
</button>
```

- **Do NOT use** `capture="environment"` — forces camera only, bypasses photo library
- **Include** `.HEIC,.heic` explicitly in `accept` — `image/*` misses HEIC in some iOS Safari versions
- **Do NOT** use `<label htmlFor>` pattern for the file input trigger — explicit `.click()` gives more control over when the picker opens

### Per-photo XHR upload

- Upload photos **sequentially** — one XHR at a time (index 0, then 1, then 2…)
- **Do NOT** upload in parallel — mobile networks at events are congested; sequential is more reliable
- Use XHR (not fetch) for real `progress` events: `xhr.upload.addEventListener('progress', handler)`
- Endpoint: `POST /api/upload/[slug]` — `multipart/form-data` with `file` (binary) + `nickname` (string)
- Server assigns filename: `{nickname}_{paddedIndex}.jpg` (e.g. `Sarah_001.jpg`)
- HEIC→JPEG conversion happens server-side (INFRA-02) — client sends original HEIC bytes

### Disabled and loading states

| Element | Disabled condition | Appearance |
|---------|-------------------|------------|
| "Continue →" button | `nickname.trim() === ""` | `opacity-50 cursor-not-allowed` |
| "Upload N photos →" button | `files.length > photoLimit` OR `uploadInProgress` | `opacity-50 cursor-not-allowed` |
| "Change photos" link | `uploadInProgress` | `opacity-50 pointer-events-none` |
| File input | `uploadInProgress` | `pointer-events-none` (via parent state) |

### Progress bar fill animation

```css
/* On the fill element */
transition-property: width;
transition-duration: 150ms;
transition-timing-function: ease-out;
```

Width set via inline style: `style={{ width: `${Math.round(progress * 100)}%` }}`.

On photo complete: fill animates to 100% → after 300ms delay, replace bar + percentage with `✓` checkmark.

### Viewport and scroll behaviour

- Each step must fit within a 375×667px viewport (iPhone SE size — the minimum target) without scrolling
- **Exception:** Photo list in Step 2 (when > 5 photos selected) scrolls within a `max-h-[220px] overflow-y-auto` container — the rest of the page (heading, CTA) stays fixed visible
- Step 3 photo progress list scrolls if > 5 photos: same `max-h-[220px] overflow-y-auto` container
- `touch-action: manipulation` on all buttons — prevents 300ms iOS tap delay

### Before-unload warning

- During Step 3 (upload in progress): browser default `beforeunload` confirmation ("Leave site? Changes you made may not be saved") is sufficient — **do not implement a custom dialog**
- Outside of upload in progress: no `beforeunload` listener
