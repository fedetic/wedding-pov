<objective>
Promote the GCP OAuth app from "Testing" to "In production" so the organizer's refresh token never expires mid-event. Then force the organizer to reconnect Google Drive (revoke + reconnect) to obtain a fresh non-expiring refresh token under the production app. Finally, verify the token auto-refresh path works by deliberately expiring the access token in the DB and confirming an upload still succeeds.

Purpose: In Testing mode, Google invalidates every refresh token after 7 days. A wedding could easily span a window where the token was issued more than 7 days ago — catastrophic if it fails during the event. Production status removes that expiry.

Output: GCP app in Production status + organizer Drive reconnected + token refresh path confirmed.
</objective>

<task type="checkpoint:human-action">
  <name>Task 1: Promote GCP OAuth App from Testing → Production</name>

  <what-to-do>
Follow these exact steps in GCP Console to publish your OAuth app:

**Step 1 — Open the OAuth consent screen**
1. Go to https://console.cloud.google.com
2. Select your `wedding-pov` project from the project picker (top-left dropdown)
3. In the left sidebar: **APIs & Services → OAuth consent screen**

**Step 2 — Check current status**
The "Publishing status" section will show **"Testing"**. Confirm this before proceeding.

**Step 3 — Click "Publish App"**
Click the **"PUBLISH APP"** button in the Publishing status section.

Google will show a confirmation dialog asking if you're ready to publish. It will mention that publishing makes the app available to any Google account user.

**Step 4 — Fill in the OAuth verification form (if prompted)**

Google may require you to provide information before publishing. Use these values:

| Field | Value |
|-------|-------|
| App name | `wedding-pov` (or your display name) |
| User support email | your email address |
| Authorized domains | your Railway domain (e.g. `wedding-pov-production.up.railway.app`) |
| Developer contact email | your email address |
| Scopes | `https://www.googleapis.com/auth/drive.file` |

**Important scope note:** The app uses `drive.file` (not `drive`). This is a **restricted scope** that only affects files created by the app itself — Google's review process for `drive.file` is faster than for the full `drive` scope.

**Step 5 — Submit and wait**

After clicking "Confirm" or "Publish":

- If Google approves immediately: status changes to **"In production"** — you're done ✅
- If Google flags it for review: you'll receive an email. Reply promptly with the app description.

**What to write if Google asks for an app description:**
> "This app allows an individual to collect photos from guests at their private wedding or event. Guests upload photos to the organizer's Google Drive folder using a QR code link. The app only accesses files it creates (drive.file scope)."

**Step 6 — Confirm final status**

After publishing, the OAuth consent screen should show:

```
Publishing status: In production
```

If it still shows "Testing" after a few minutes, refresh the page.

<task type="checkpoint:human-action">
  <name>Task 2: Revoke + Reconnect Google Drive to Get a Non-Expiring Refresh Token</name>

  <what-to-do>
The refresh token currently stored in the database was issued when the app was in Testing mode. That token **will expire 7 days after it was issued**, regardless of the app's new Production status. You must get a fresh refresh token issued under the Production app.

**Why a fresh token is needed:**
Google issues refresh tokens that carry the app's "mode" at the time they were issued. Promoting to Production does not retroactively make existing tokens permanent. A new OAuth flow is required.

---

**Step A — Revoke the existing token in Google's account settings**
1. Go to https://myaccount.google.com/permissions
2. Find **"wedding-pov"** in the list of apps with access
3. Click it → click **"Remove access"**
4. Confirm removal

This ensures Google's side has no stale token.

---

**Step B — Delete the existing token row from the database**

Run this SQL against your Neon database (Neon console → SQL Editor, or via a local `psql` connection using your `DATABASE_URL`):

```sql
-- Preview what will be deleted (run this first)
SELECT id, user_id, connected_at, access_token_expires_at
FROM google_tokens;

-- Then delete (replace 'YOUR_USER_ID' with the actual user_id from the SELECT above)
DELETE FROM google_tokens
WHERE user_id = 'YOUR_USER_ID';
```

> **Alternative:** If you'd rather not delete the row, you can just run the reconnect flow — the `/api/drive/callback` route upserts the token row. But deleting first is cleaner and avoids any stale state.

---

**Step C — Reconnect Google Drive in the app**
1. Log in to your wedding-pov dashboard: `https://wedding-pov-production.up.railway.app/dashboard`
2. Click **"Connect Google Drive"** (or equivalent button on the dashboard)
3. Complete the OAuth flow — sign in with your Google account
4. You will see the Google consent screen. This time it will show **"In production"** branding.
5. Grant access → you'll be redirected back to the dashboard with "Drive connected ✓"

---

**Step D — Confirm the new token is stored**

Verify the new token row is in the DB:

```sql
SELECT user_id, access_token_expires_at, connected_at, updated_at
FROM google_tokens;
```

Expected: `connected_at` is within the last few minutes. `access_token_expires_at` will be ~1 hour from now (that's normal for access tokens — the **refresh token** stored in `encrypted_refresh_token` is now non-expiring).

---

**What a successful reconnect looks like:**
- Dashboard shows "Drive connected" state
- `google_tokens` has a fresh row with `connected_at` = now
- The `encrypted_refresh_token` column contains an AES-256-GCM encrypted token issued under the Production app
  </what-to-do>

  <resume-signal>
Type "reconnected" once you've completed all four steps (revoke, delete DB row, reconnect, confirmed DB row exists).
  </resume-signal>
</task>

<task type="auto">
  <name>Task 3: Verify Token Auto-Refresh — Force-Expire Access Token and Trigger Upload</name>
  <files>No files modified — DB-only test using SQL + curl</files>
  <action>
Force the access token to appear expired in the DB, then trigger a real upload to confirm that googleapis auto-refreshes the access token using the stored refresh token. This validates the token refresh path end-to-end.

**Step 1 — Force-expire the access token in the DB**

Run against Neon (SQL Editor or psql):

```sql
-- Set access_token_expires_at to 1 hour in the past
UPDATE google_tokens
SET access_token_expires_at = NOW() - INTERVAL '1 hour',
    updated_at = NOW()
WHERE user_id = (SELECT id FROM "user" LIMIT 1);

-- Confirm the update
SELECT user_id, access_token_expires_at, updated_at FROM google_tokens;
```

The `access_token_expires_at` should now be in the past. The `access_token` column still has the old (now effectively invalid) value — this simulates the state the app will be in between token refresh cycles.

**Step 2 — Upload a test photo through the guest upload page**

1. Open any active event's guest upload URL: `https://wedding-pov-production.up.railway.app/e/[slug]`
2. Enter a nickname (e.g. "TokenTest")
3. Select any JPEG photo (1–2 files)
4. Upload

**Step 3 — Confirm success**

Expected outcomes:
- Upload succeeds (200 response, completion screen shown)
- Photo appears in the Drive folder attributed as `TokenTest_[filename].jpg`
- `google_tokens` row updated with a fresh `access_token_expires_at` approximately 1 hour from now:

```sql
SELECT user_id, access_token_expires_at, updated_at FROM google_tokens;
-- access_token_expires_at should be ~1 hour from NOW(), not in the past
```

**What this proves:** googleapis used the stored `encryptedRefreshToken` to silently obtain a new access token, persisted it back to the DB via the `tokens` event listener in `drive-upload.ts`, and the upload completed successfully. This exact path will run on the wedding day when the cached access token expires after ~1 hour.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GCP Console → DB | GCP issues a new refresh token; app stores it AES-256-GCM encrypted. Trust boundary: only the server has the AES key. |
| Organizer browser → /api/drive/callback | OAuth callback receives the code; code is server-exchanged for tokens. Tokens never appear in client-side JS. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-01 | Information Disclosure | google_tokens.encryptedRefreshToken | mitigate | AES-256-GCM encryption already in place (Phase 1). Refresh token never appears in logs, responses, or client code. |
| T-04-02 | Elevation of Privilege | GCP OAuth scope | mitigate | App uses `drive.file` (not `drive`). Confirmed during Production promotion — consent screen lists only `drive.file`. |
| T-04-03 | Spoofing | OAuth redirect_uri | mitigate | `GOOGLE_REDIRECT_URI` env var locks the callback to the Railway domain. GCP console has only one authorized redirect URI. |
| T-04-04 | Denial of Service | Testing-mode token expiry | mitigate | This plan's entire purpose — Production promotion eliminates 7-day expiry risk. |
</threat_model>
