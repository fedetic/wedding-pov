# Milestone v1.0: Wedding POV MVP

**Status:** ✅ SHIPPED 2026-05-04
**Phases:** 1–4
**Total Plans:** 12

## Overview

Four phases from zero to a live, wedding-ready photo upload app. Phase 1 established the organizer account and Drive OAuth token architecture. Phase 2 delivered event management and QR codes. Phase 3 built the complete guest upload experience — the core value of the product. Phase 4 hardened the system for real-world use: OAuth production verification, mobile polish, and end-to-end validation before the wedding day.

## Phases

### Phase 1: Foundation + Auth

**Goal**: Organizer can create an account, log in, and connect Google Drive — the system has everything it needs to store photos securely
**Depends on**: Nothing (first phase)
**Requirements**: AUTH-01, AUTH-02, AUTH-03
**Success Criteria:**
1. Organizer can register with email and password and land on a dashboard
2. Organizer can log back in with their credentials after logging out (logout is v2; login persistence is the testable criterion here)
3. Organizer can click "Connect Google Drive," complete the OAuth flow, and see a "Drive connected" confirmation
4. Drive access persists after session expiry — refresh token is stored and works without re-auth
5. App is deployed and reachable at a public Railway URL
**Plans**: 4 plans

Plans:
- [x] 01-01-PLAN.md — Bootstrap Next.js 15, install deps, Drizzle schema (7 tables), drizzle-kit push to Neon
- [x] 01-02-PLAN.md — Better Auth config, auth API route, middleware, Register + Login forms, Dashboard shell
- [x] 01-03-PLAN.md — Google Drive OAuth routes (/api/drive/connect, /api/drive/callback), AES-256-GCM token encryption
- [x] 01-04-PLAN.md — Railway deployment, env vars, GCP redirect URI registration, smoke test all auth flows

### Phase 2: Events + QR

**Goal**: Organizer can create events, generate scannable QR codes, and have Drive folders ready to receive photos
**Depends on**: Phase 1
**Requirements**: EVENT-01, EVENT-02, EVENT-03, QR-01, INFRA-01
**Success Criteria:**
1. Organizer can create an event with a name and photo limit, and it appears in their event list
2. A Google Drive folder named after the event is automatically created in the organizer's Drive when the event is saved
3. Organizer can toggle an event active or inactive — inactive events will reject guest uploads
4. Organizer can download a print-ready PNG QR code for any event
5. Scanning the QR code opens the correct `/e/[slug]` upload page URL in a mobile browser
**Plans**: 3 plans

Plans:
- [x] 02-01-PLAN.md — Backend: install deps (qrcode, nanoid), createEvent Server Action (Drive folder + DB insert + slug), PATCH toggle API route
- [x] 02-02-PLAN.md — Dashboard UI: EventList (Server Component), EventRow (optimistic toggle), CreateEventForm, /dashboard/events/new page, update dashboard
- [x] 02-03-PLAN.md — QR feature: QRModal component (256px QR generation, PNG download), wire into EventRow

### Phase 3: Guest Upload

**Goal**: Guests can scan the QR code, enter their name, upload photos, and see them land in the organizer's Google Drive — with no app install and no account
**Depends on**: Phase 2
**Requirements**: GUEST-01, GUEST-02, GUEST-03, GUEST-04, GUEST-05, INFRA-02, INFRA-03, INFRA-04
**Success Criteria:**
1. Guest can open the upload page in iOS Safari or Android Chrome by scanning the QR code — no app install required
2. Guest can enter a nickname and select up to the event's configured photo limit (server enforces the limit)
3. Guest sees a per-photo progress indicator during upload and a clear "Upload complete ✓" confirmation when all photos are done
4. Photos appear in the correct Drive folder attributed by guest name (e.g. `Sarah_001.jpg`, `Sarah_002.jpg`)
5. HEIC files from iPhones are converted to JPEG before Drive upload; the upload endpoint rejects abusive burst requests; Drive tokens never appear in any guest browser request
**Plans**: 3 plans

Plans:
- [x] 03-01-PLAN.md — Upload API: RateLimiterMemory (30/15min per IP:slug), OAuth2-brokered Drive upload with HEIC→JPEG conversion, POST /api/upload/[slug] route handler
- [x] 03-02-PLAN.md — Guest UI: Mobile-first upload page with sequential XHR state machine (landing → nickname → photo select → upload → complete/error), terracotta-rose palette, HEIC support
- [x] 03-03-PLAN.md — E2E Verification: middleware audit, build check, token leak audit, mobile flow confirmation on iPhone iOS Safari

### Phase 4: Launch Readiness

**Goal**: The system is verified, mobile-polished, and safe to run on a real wedding day — OAuth tokens won't expire mid-event, uploads work on real phones, and the full flow is confirmed end-to-end
**Depends on**: Phase 3
**Requirements**: *(no additional v1 requirements — this phase validates and hardens what phases 1-3 built)*
**Success Criteria:**
1. Google Drive OAuth app is in "Production" status in GCP Console — refresh tokens do not expire after 7 days
2. Full guest flow (scan → nickname → select photos → upload → confirmation) works on an actual iPhone (iOS Safari) and Android phone (Chrome)
3. Photos from the test run appear in Drive with correct guest name attribution and no corruption
4. Inactive events correctly reject upload attempts with a clear error message

## Milestone Summary

**Key Decisions:**

- Railway (not Vercel) — 4.5 MB Vercel body limit blocks photo uploads
- Better Auth — DB-backed sessions, Drizzle adapter, avoids NextAuth JWT complexity
- Server-brokered resumable upload — Drive tokens never reach guest browser
- `drive.file` scope (not `drive`) — wrong scope triggers weeks-long Google security review
- AES-256-GCM token encryption — refresh tokens encrypted at rest in Neon DB
- `heic-convert` CJS import — v2.1.0 is CommonJS, not ESM; direct named import used
- Fail-open rate limiter — rate limiter errors don't block uploads to avoid degraded UX on rate-limiter bugs
- Drive upload record failure non-blocking — file is already in Drive; DB insert failure is logged but doesn't fail the HTTP response

**Issues Resolved:**

- GCP OAuth consent screen "Testing" mode causes 7-day refresh token expiry — resolved by promoting to Production (Phase 4)
- `db.query.events.findFirst()` requires Drizzle relations — resolved by using `db.select()` pattern
- `heic-convert` v2.1.0 ships as CJS, not ESM — resolved by using direct named import

**Issues Deferred to v2:**

- Organizer log out
- Disconnect / reconnect Drive
- Per-guest photo retry
- In-app upload history per event
- Shareable event link (URL alongside QR)

**Technical Debt:**

- Android Chrome E2E test not performed (no device available) — primary audience is iPhone; test opportunistically before next wedding
- Rate limiter IP trust: `X-Forwarded-For` trusted as-is; acceptable given Railway always sets this header, but could be spoofed in proxy-less deployment
